DiagramHQ: a UX teardown

A model-first architecture tool with an exceptional thesis and a fragmented product. The idea beats IcePanel; the implemented experience does not yet exist as one coherent tool. This review traces every significant workflow through the actual code and turns the gaps into a prioritized roadmap.

METHOD · source-grounded SURFACES READ · studio, canvas, workspace, dashboard, share REFERENCES · IcePanel, draw.io, Lucidchart, Miro/FigJam, Excalidraw, Structurizr STATE · Phases 01–04 "complete"

00Executive summary

The thesis is the strongest thing here, and it is not yet in the product. DiagramHQ's premise — objects are the source of truth, diagrams are disposable projections, drilling down is navigation over one model — is a genuinely better mental model than draw.io and a cleaner one than IcePanel. The domain layer actually implements it. The UI the user touches does not.

There are four separate front doors, each a different product, and no single coherent editor behind them:

  1. /studio — the flagship React Flow editor. Rich, dark, login-free. But it is a single-canvas drawing tool that saves one JSON blob into workspace.settings.studioDiagram. It does not read or write the objects/connections/views API.
  2. /dashboard + /workspace/[id]/* — a light-theme CRUD app branded "Architecture OS", exposing raw org slugs and user IDs, with a small embedded canvas fed by hard-coded sample objects.
  3. /canvas/[workspaceId]/[diagramId] — a second, hand-rolled SVG canvas (not React Flow) with its own select/connector/hand tool modes and hard-coded L1/L2 node sets, ignoring its own route params.
  4. /share and /mobile — further standalone views.

Inside the flagship, the two features that are supposed to make this an architecture tool rather than a drawing tool are cosmetic:

  • C4 drill-down does nothing to the canvas. Switching Context → Container → Component changes a breadcrumb label and a sidebar highlight. displayNodes never filters by c4Level (app/studio/page.tsx:1169). You see the same graph at every "level."
  • "Views" are badge overlays on one canvas, not independent saved projections with their own membership and layout. Security / Data / Ownership toggle a flag that lights up badges on the same nodes.

And a large share of the top bar is a demo shell: presence cursors are three hard-coded teammates, the AI copilot / generation / review / ADR features are deterministic domain functions (not model calls), the pull request, branches, snapshots and visual diff are seeded fixtures. These are impressive to click through and misleading to rely on.

The net: a first-time architect sees a dense, confident interface and a beautiful reference diagram, then hits a wall the moment they try to do the things the landing page promises. The work ahead is less "add features" and more collapse four half-products into one real model-first editor, then make the model-first behaviors actually work.

03Strengths — do not change these

The model-first thesis

Objects independent of diagrams, connections as first-class typed entities, views as projections, stable IDs for canvas / API / agents. This is a better foundation than draw.io (file of shapes) and cleaner than IcePanel. Protect it.

The domain layer

@diagramhq/domain is framework-free and enforced by check-architecture. Layouts, projections, invariants, filters and templates are real and unit-tested. The hard part is done; the UI just isn't using it.

The model navigator

The studio left sidebar — objects grouped by kind, live counts, instant search, inline quick-create, per-category "+" — is genuinely better than draw.io's flat shape tray and competitive with IcePanel's tree.

Login-free instant start

/studio opens straight into a laid-out reference architecture with no signup. This is a better cold-open than IcePanel (which gates behind an account) and matches draw.io's best trait.

Undo as a command stack

A real command-pattern dispatcher with optimistic apply + rollback-on-failure for moves, align, layout, create, connect, delete. The architecture is right; it just needs to cover every mutation.

Auto-layout range

Layered, grid, radial and force-directed via a registry, one click from the canvas. draw.io buries layout in a submenu; Excalidraw has none. This is a real speed advantage for architecture graphs.

Better than IcePanel today: the no-login open, the single-screen density, and the breadth of one-click layouts. Better than draw.io today: the typed object navigator and the fact that an object is a thing, not a shape. Keep all of these intact through any redesign.

04Critical UX problems

Each follows: observation → user problem → why it matters → competitive reference → recommendation.

CRITICAL

Four disconnected products wearing one name

Observation
Three independent canvas implementations (/studio React Flow, /canvas/* hand-rolled SVG, the embedded workspace canvas) with different tool models, plus a light CRUD dashboard. Nothing you make in one appears in another.
User problem
The tool you get depends on which URL you landed on. Work doesn't carry. The mental model resets every navigation.
Why it matters
Coherence is usability. A user cannot build a workflow on a product that is actually four products.
Reference
IcePanel, Lucidchart and Figma each have exactly one editor reached many ways. The surface is consistent no matter how you arrive.
Recommendation
Pick /studio's React Flow editor as the one true canvas. Delete the hand-rolled /canvas/* implementation. Make the workspace shell host the same editor on real data. One editor, one interaction model.
CRITICAL

The model-first promise isn't realized in the editor

Observation
Studio holds nodes/edges in local React state and autosaves one blob. It never calls the objects/connections/views endpoints. "One object, many views" has no UI expression — there is one canvas.
User problem
Priya cannot reuse an object across views, cannot fork current vs. future, cannot trust that the diagram reflects a model — because there is no model behind the diagram she's editing.
Why it matters
This is the entire reason to choose DiagramHQ over draw.io. Without it, it's a worse draw.io.
Reference
Structurizr and IcePanel both make the model the document and views queries over it. That is the category.
Recommendation
Wire studio to the real model API: objects persist as objects, the canvas is a view with its own membership + layout, adding the same object to a second view is a first-class action.
CRITICAL

C4 drill-down is a label, not navigation

Observation
Context/Container/Component tabs update a breadcrumb and sidebar state only; the canvas graph is identical at all three levels (displayNodes ignores c4Level).
User problem
Clicking into a system expecting to see its internals shows the same picture. The signature architecture interaction silently fails.
Why it matters
Drill-down is the #1 job for the newcomer persona (Alex) and the explanation job for the leader (Dana).
Reference
IcePanel's double-click-to-descend and Structurizr's level views are the whole point of C4 tooling.
Recommendation
Make level switching a real filter over a parent/child hierarchy; double-click a system to descend, breadcrumb to ascend.
CRITICAL

Simulated features presented as real

Observation
Presence (3 hard-coded peers), comments, PR review, branches, snapshots, visual diff, and all four "AI" actions are seeded fixtures or deterministic domain functions — not live collaboration or model calls.
User problem
A user who shares a link, assigns a comment, or trusts an "AI review" is relying on nothing. Discovering this destroys trust in the parts that are real.
Why it matters
A trial that feels like a stage set converts worse than a small honest tool.
Reference
n/a — this is a credibility problem, not a feature gap.
Recommendation
Hide everything not wired to real data behind a clearly labeled "Preview / coming soon" state, or remove it from the default toolbar. Ship fewer, true things.
HIGH

The top bar has ~25 equal-weight controls

Observation
A single 56px header crams C4 tabs, view switcher, persona select, sign-in, branch, presence, versions, diff, PR, comments, icons, export, mermaid, plantuml, share, copilot, AI-gen, AI-review, ADR, mobile, demo-loader, import, export-JSON, reset, trace, inspector (app/studio/page.tsx:1507–1804).
User problem
Nothing is primary, so nothing is findable. The most common actions (add, connect, name) are not even in the bar; they're buried or implicit.
Why it matters
Visual hierarchy is how a user learns what to do next. This bar teaches nothing.
Reference
Figma: a small left tool cluster, a contextual right panel, everything else in menus / ⌘K. IcePanel keeps the top bar to model-level actions.
Recommendation
Reduce to ~5 primary controls; move the rest into a command palette, an overflow menu, and context-sensitive panels.

06Canvas experience

What works

  • Infinite pan/zoom, minimap, fit-to-view, fullscreen, focus mode (dims non-selected), and a group-move that snaps as a rigid body and reverts on persistence failure — all solid.
  • Auto-layout is one click and genuinely useful on architecture graphs.
  • Dragged positions persist and survive parent re-renders (a real bug that was fixed recently — good).

What fights the user

HIGH

Two competing zoom/pan clusters + colliding panels

Observation
React Flow's native <Controls> (bottom-left) and a custom pan/zoom toolbar (top-right) both exist; the auto-layout menu also anchors bottom-left, on top of the native controls.
Impact
Redundant, conflicting affordances; overlapping hit targets on small screens.
Recommendation
Keep one zoom cluster (bottom-right, Figma convention). Drop React Flow's default Controls. Give the layout menu its own corner.
HIGH

Box-select is a mode toggle, not the default

Observation
Drag-select only works after toggling a "Box Select" button (or holding Shift); selectionOnDrag is off by default.
Impact
Every tool the user already knows (Figma, Miro, draw.io, Excalidraw) drag-selects on empty canvas by default. Here, dragging empty space does nothing until you find a button.
Recommendation
Make drag-on-empty-canvas marquee-select by default; keep space-to-pan. This is a one-line default change with outsized payoff.
HIGH

No right-click context menu anywhere

Observation
Zero onNodeContextMenu / onPaneContextMenu handlers in the codebase.
Impact
The universal "right-click the thing → act on the thing" expectation fails. Every object action requires a trip to the inspector or a hidden shortcut.
Recommendation
Add a context menu on node, edge and pane: rename, duplicate, delete, add connection, bring to front, add to view, drill in.

At scale (hundreds of objects)

The canvas has not been designed for density. Everything renders every frame (no virtualization / LOD), there is no collapse-to-boundary for groups, no semantic zoom (labels at 10% zoom are unreadable), and focus mode is the only tool for isolating a subgraph. A real architecture of 300+ objects will be slow and unnavigable. This is acceptable for now — but it means large-diagram UX is a future workstream, and the drill-down fix is also the scale fix (you navigate levels instead of one giant graph).

08Information architecture

The hierarchy on paper — Organization → Workspace → Architecture → (Objects, Connections, Views, Flows, Decisions) — matches the architect's mental model well. The exposure of it does not.

  • The flagship editor lives outside the hierarchy. /studio has no workspace, no architecture, no view. The dashboard → workspace path (where the hierarchy lives) uses a different, weaker canvas. A user cannot tell where their work belongs.
  • Internal model leaks to the surface. The dashboard shows org slug, org id, and User ID as primary content; the workspace header shows the raw workspaceId. Users should never see these — they're implementation, not information.
  • Two brand names. The dark editor says "DiagramHQ"; the dashboard says "Architecture OS." Same product, two identities.
  • "Diagrams" vs "Views" vs "Levels" are three names for overlapping ideas exposed to the user at once (sidebar tabs + C4 tabs + perspective switcher). The user must hold three mental models of "a way of looking at the model."

Progressive disclosure opportunity: the user should never need to know the words "projection", "version id", "workspace id", or "C4 level number" to do the common jobs. Hide org/workspace plumbing behind a single project switcher; present "views" as the one concept and let level and perspective be properties of a view.

09Interaction model

Predictable

Single-click selects, click-empty deselects, drag moves, drag-from-handle connects, ⌘Z undoes moves. These match convention.

Missing conventions

No right-click menu. No double-click to rename a node or label an edge. No ⌘C/⌘V/⌘D. No ⌘K command palette (README lists it as "pending" since Phase 02). No discoverable shortcut list — the ~8 shortcuts that exist (F, M, Space, Shift+F, Alt+F) are hidden in button tooltips only.

Inconsistent

Creating a node via the palette goes through the undoable command stack; creating/connecting from the inspector mutates state directly and cannot be undone. The same logical action has two code paths with different guarantees.

Borrow directly: draw.io's hover-arrow-to-create-and-connect, Figma's ⌘K + double-click-to-edit, Miro's drag-from-empty-to-marquee. These are well-understood patterns; copying them is pure upside here.

Error prevention & recovery

  • No inline window.confirm fallback awareness: the "Reset / clear diagram" action uses window.confirm — fine in-app, but the destructive clear is a top-bar button one click from the primary workspace, with only a native dialog between the user and total loss.
  • Undo doesn't cover metadata, so an accidental rename or retyped description is unrecoverable via ⌘Z.
  • No invalid-connection prevention — any handle connects to any handle; the typed model that could forbid nonsensical links isn't consulted.
  • Autosave status is honest and well done (saving / saved / saved-local / cloud vs guest) — a genuine bright spot in system-status feedback.

Accessibility

Keyboard-only users cannot create or connect nodes (both require pointer drag). Many controls are emoji + hidden text, so the meaning depends on an emoji glyph. Focus states exist on links but not consistently on canvas controls. Color alone carries meaning in the view overlays (security/data/ownership badges). Treat as a dedicated later pass; none of it is a quick win, but the emoji-as-icon habit should stop now in new UI.

12The draw.io architect walks in

Immediately better

Opens with a real, auto-laid-out architecture — no blank page. A typed object navigator with search instead of a shape tray. Brand-icon picker for tech. One-click layouts. "This clearly knows what a service is."

Immediately worse

Can't double-click to rename. No right-click. No copy/duplicate. Dragging empty space does nothing. The toolbar is a wall. "Why is the easy stuff hard?"

Confusing

C4 tabs change nothing visible. "Views" don't make new diagrams. The AI button produces a canned result. Signing in drops them into a different, uglier app that shows database IDs. "Which one is the real product?"

After 30 minutes, what makes them switch from draw.io?

Only one thing, and it isn't built yet: "I edited the object once and it updated everywhere, and I drilled from the context view into the container view of the same model." That single true experience is worth more than all 25 toolbar buttons. Nothing else will pull a draw.io user across, because for pure drawing draw.io is faster today.

What makes them choose IcePanel over DiagramHQ?

IcePanel delivers the model-first experience now — real drill-down, real reuse, real teams — with conventional canvas interactions and without the uncanny feeling that half the buttons are props. DiagramHQ wins only once its model behaviors are real and its canvas stops surprising people.

14Recommended product principles

  1. Model once, draw never twice. Every edit is to the model; a diagram is a disposable view. If a change doesn't propagate, it's a bug.
  2. Nothing in the UI is a prop. A control that doesn't act on real data is labeled "Preview" or isn't shipped. Trust is the moat.
  3. The canvas never surprises a Figma user. Right-click acts, double-click edits, empty-drag selects, ⌘K finds. Convention first, cleverness second.
  4. Hide the plumbing. No user should see a workspace id, version id, or the word "projection" to do a common job.
  5. Depth is navigation, not a label. Levels and views are ways to move through one model, and they must actually move you.
  6. Common actions cost one or two interactions. Measure the top ten workflows in clicks; defend the budget.
  7. One tool, many doors. However you arrive — share link, dashboard, deep link — you land in the same editor on the same model.
  8. We model software; we are not a whiteboard. Correctness and reuse over drawing freedom. Say no to Miro parity.

15Top 10 changes, in order

  1. Gate or remove every simulated feature. Cheapest possible trust repair; do it first.
  2. Inline rename + edge labels (double-click). Removes the most frequent friction.
  3. Right-click context menus on node/edge/pane carrying rename, duplicate, delete, connect, drill-in.
  4. Copy / paste / duplicate + default marquee-select. Canvas-convention parity.
  5. Make C4 drill-down real. The signature interaction must work.
  6. Wire the editor to the model API. Objects persist as objects; the canvas is a view.
  7. Collapse to one editor inside the workspace. Delete the hand-rolled canvas and the duplicate zoom cluster.
  8. Command palette (⌘K) over objects + actions; route all mutations through undo.
  9. Slim the top bar to five primary controls; everything else to palette/overflow/context panels.
  10. Hide org/workspace IDs; one brand, honest landing copy.

Before large changes: instrument the editor (event tracking on add/connect/rename/drill/undo), record baseline interaction counts for the ten workflows in §19, run 5 moderated trials with real architects on the "drill into a system and reuse an object" task, and define activation = first real object persisted to a model (not a blob saved). No new functionality in Phase 1 beyond what removes top friction.

Phase 2 — Core workflow optimization

Target the 80% actions: make add/connect/edit/move/select/search/undo fast and identical everywhere. Collapse the top bar to five primary controls + ⌘K palette + overflow. Route every mutation through the command stack so undo is total. Measure each workflow before/after (§19).

Phase 3 — Architecture-specific differentiation the moat

Now make the category behaviors real: wire the editor to the model API; C4 drill-down as navigation over a parent/child hierarchy; one object in many views with per-view layout; current/future forking; model validation surfaced as gentle warnings. Primary differentiators to pursue: (1) model-as-single-source with live propagation, (2) real drill-down, (3) query-the-model for security/ownership questions. These, not drawing, are why anyone leaves IcePanel or draw.io.

Phase 4 — Power-user experience

Palette actions for everything, bulk edit of selection metadata, reusable object library, smart alignment guides, templates that instantiate real model objects, navigation shortcuts between views. Goal: an expert is measurably faster here than in draw.io.

Phase 5 — Collaboration & communication

Split "building the architecture" from "communicating it." Real presence/comments on live data; a polished read-only explorer and architecture walkthrough (flow playback on real flows); deep links to a specific view/object; export that reflects the model. The share viewer and persona overlays are the seed — make them real.

Phase 6 — Polish & delight

Only after the above: empty states, onboarding, transitions, accessibility, replace emoji-icons with a real icon set, loading states. Never ahead of workflow fixes.

  • Activation: % of first sessions that persist ≥1 real object to a model (not a blob). North star.
  • Drill-down usage: % of sessions that descend at least one C4 level (today: ~0, because it doesn't work).
  • Reuse rate: % of objects appearing in ≥2 views — the single best proxy for "model-first is landing."
  • Interaction cost for the ten §20 workflows, tracked against targets.
  • Edit-after-create rate: % of created objects that get named (today the inspector tax suppresses this).
  • Undo frequency & failed-undo (an undo that didn't change anything = a coverage gap).
  • Time-to-first-connected-pair and time-to-first-shared-view.
  • Trial-to-trust: qualitative — do users in moderated tests ever say "wait, is this real?" (target: never).

Deliberately not tracking vanity counts (buttons clicked, diagrams created) — they'd look healthy today precisely because the tool rewards drawing over modeling.

21Competitive gaps to close

vs IcePanel

IcePanel does better: real drill-down, real reuse across diagrams, real teams/presence, conventional canvas. Must close: drill-down, reuse, model-wiring. Worth closing: presence/comments. Not strategic: matching their exact visual style — DiagramHQ's density and no-login open are its own.

vs draw.io

draw.io does better: raw drawing speed, flexibility, familiarity, keyboard flow, templates, export. Match: inline edit, right-click, clipboard, marquee — table stakes. Exceed: typed objects + layout + model. Ignore by philosophy: arbitrary freeform shapes and unrestricted drawing — that's the anti-persona.

vs Miro / FigJam / Lucidchart

Worth adopting: Lucidchart's conditional/data-linked formatting (maps straight onto typed metadata), Miro's frictionless multiplayer and presentation mode, FigJam's effortless onboarding. Adopt the interaction polish, not the freeform canvas.

Opportunities no competitor nails

(1) A model an AI agent can safely edit with evidence — IcePanel and draw.io are human-only; this is the clearest open lane. (2) Querying architecture ("every path PII takes to a third party") — nobody makes this a first-class, answerable question. (3) Automatic truth — a model that updates itself from infra/code so diagrams can't rot. Win one of these decisively and the category shifts.

22Do not build yet

More AI buttons

A fifth deterministic "AI" action adds surface and subtracts trust. No new AI UI until one is a real model call.

Enterprise shell (SSO/SCIM/RBAC/billing modals)

These modals exist already and solve nothing for a product with no working core. Freeze until activation is real.

More export formats

Mermaid + PlantUML + PDF + SVG + PNG + JSON already outnumber the real features. Stop adding; make export reflect the model.

Freeform drawing tools

Shapes, sticky notes, freehand — this is the anti-persona. Saying no here is strategy.

Mobile editing

A companion view is fine; full mobile editing of architecture is premature polish.

Cosmetic theming / animations

No micro-interaction work while double-click-to-rename is missing.
